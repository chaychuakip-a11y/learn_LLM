# 10 做出你自己的第一版

先完成20条独立真实问题单的试点，再扩展到200条左右。数字是工程起步规模，不是效果保证。覆盖“目标未进候选、候选输给其他分支、词典缺项、图路径问题、资源加载不符、证据不足”等真实类别，兼顾主要语种。不要用同一案例的多种问法填满数据量。

## 每个里程碑交付一个可回读产物

| 阶段 | 产物 | 通过条件 |
| --- | --- | --- |
| 理解项目 | demo与小实验 | 能解释脚本、stdout、结论和loss |
| 数据试点 | 20例快照 | 原文与版本可追溯，缺材料明确 |
| 教师试点 | 两个教师的候选批次 | 实际执行工具，失败保留 |
| 审核划分 | reviewed_v1与split_report | 每条有审核人，同源不跨组 |
| 训练冒烟 | 20步与checkpoint | 有限数值、显存可控、保存恢复可用 |
| 第一版 | adapter与测试报告 | 相对原模型有可解释改善，无关键回归 |
| CPU试点 | 量化文件与吞吐记录 | 同协议可用，质量与完整耗时满足实际要求 |

## 继续开发在哪里改

新dump字段：先扩展自己的归一化解析器，再更新analysis只读函数与合成测试。新工具：更新protocol和相同的训练目标/运行协议，不能只改推理。新标签类型：补审核规则和评测维度。RAG：另建版本化知识/案例索引，排除测试答案和同组未来材料；当前代码没有假装实现检索服务。

重要的失败优先补真实独立案例和正确证据；样本少时别先加epoch。保留数据版本、基座版本、依赖版本、run_manifest、模型与量化版本、评测结果，形成一张实验对照表。

学到这里，你应该能独立回答：输入有哪些？教师为什么这样查？哪些位置算loss？每张卡做什么？模型重载后如何验证？量化是否改变了结果？某条新单失败该先看哪里？

现在仍由内网验收的部分：真实API、私有dump解析、Gemma模板、V100训练、合并/GGUF、CentOS7吞吐。代码中的离线测试只验证工程行为，不代替这些实验。
